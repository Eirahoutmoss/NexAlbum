1. Karar Özeti
NexAlbum bir topluluk projesidir. Kod tek kişi tarafından yazılsa da, ürün topluluğa aittir.

Katkı açık. Herkes katkı verebilir: kod, şablon, profil, çeviri, doküman, test, tasarım.

Süreç şeffaf. Katkı rehberi, issue şablonları, PR şablonları kamuya açık.

Davranış kuralları var. Contributor Covenant 2.1.

İletişim kanalları net. GitHub Issues, Discussions, PR.

Yönetişim: Şu an BDFN (tek geliştirici); topluluk büyürse maintainer ekibi.

Katkıcı tanınır. AUTHORS.md, sürüm notları, teşekkür.

DCO zorunlu. CLA yok; katkıcı basit beyan imzalar.

Dil politikası: Türkçe + İngilizce serbest; kod İngilizce.

Sürdürülebilirlik: Topluluk, projenin sigortasıdır.

Bu karar, 02 (Açık Kaynak) ve 04 (Tek Kişi) kararlarının topluluk boyutudur.

2. Topluluk Felsefesi
2.1 İlkeler
Açıklık. Her tartışma, her karar kamuya açık.

Saygı. Katkıcıya, kullanıcıya, fikre saygı.

Sabır. Herkesin zamanı farklı; baskı yok.

Şeffaflık. Kararlar yazılı, gerekçeli.

Yardımseverlik. Yeni başlayana yol göster.

Kalite. Katkı, standartlara uygun olmalı.

Tanıma. Katkı görülür, teşekkür edilir.

Çeşitlilik. Farklı bakış açıları değerlidir.

Sürdürülebilirlik. Kimse tükenmesin.

Keyif. Bu bir hobi; keyif al.

2.2 Anti-ilkeler
❌ "Ben yaptım, benim" (sahiplik)

❌ Katkıcıyı küçümsemek

❌ Sessiz reddetme (gerekçesiz)

❌ Aşırı bürokrasi

❌ Toksik davranış

❌ "Burada böyle yapılır" baskısı

❌ Katkıyı kabul edip adını yazmamak

❌ Yeni başlayanı korkutmak

2.3 Topluluk kimliği
"NexAlbum topluluğu: saygılı, açık, yardımsever ve keyif alan bir grup. Birlikte, fotoğrafçıların işini kolaylaştıran ücretsiz ve açık bir araç yapıyoruz."

4.5 Şablon katkısı
Format: JSON (şema doğrulaması).

Yer: templates/community/ (ayrı repo veya PR).

Şart: Önizleme görseli + açıklama.

Kategori: Uygun kategori seçilmeli.

Test: Şema doğrulaması geçmeli.

4.6 Baskı profili katkısı
Format: JSON (şema doğrulaması).

Kaynak: Baskı evi adı belirtilmeli (varsa).

Uyarı: Topluluk profili "doğrulanmamış" olarak işaretlenir.

4.7 Çeviri katkısı
Format: .resx veya JSON.

Dil: ISO 639-1 kodu.

Kapsam: Tam çeviri tercih edilir.

Güncelleme: Ana dil değişince çeviri güncellenmeli.

4.8 Dokümantasyon katkısı

5. Katkı Süreci
5.1 Adım adım
Adım 1: Keşfet

README'yi oku.

CONTRIBUTING.md'yi oku.

good first issue etiketli issue'lara bak.

Discussions'ı göz at.

Adım 2: İletişim

Yeni katkıysan: "Merhaba, X konusunda yardım etmek istiyorum" de.

Mevcut issue'yu seç veya yenisini aç.

Yaklaşımını paylaş (kod yazmadan önce).

Adım 3: Hazırlık

Fork et.

Clone et.

Branch aç (feature/xyz, fix/xyz, docs/xyz).

Ortamı kur (README'deki talimatlar).

Adım 4: Geliştirme

Küçük adımlarla çalış.

Test yaz (zorunlu).

Kod stiline uy.

Commit mesajı anlamlı (Conventional Commits).

Adım 5: Test

Birim testleri çalıştır: dotnet test.

Kod stili: dotnet format --verify-no-changes.

Lisans kontrolü: scripts/verify-licenses.ps1.

Adım 6: PR aç

Şablonu doldur.

Ne, neden, nasıl açıkla.

Ekran görüntüsü ekle (UI değişikliği varsa).

DCO imzala: git commit -s.

Adım 7: İnceleme

CI sonuçlarını bekle.

Yorumları yanıtla.

Gerekirse düzelt.

Sabırlı ol (gönüllü proje).

Adım 8: Birleştirme

Onay sonrası birleştirilir.

Adın AUTHORS.md'ye eklenir.

Teşekkür!

5.2 Branch stratejisi

5.4 DCO (Developer Certificate of Origin)
Her commit imzalı olmalı:

bash
git commit -s -m "feat: ..."

GPL-3.0+ koşullarıyla uyumlu olduğunu,

Başkasının telif hakkını ihlal etmediğini.

CLA yok. DCO yeterli.

6. Kod İnceleme Süreci
6.1 İnceleme kriterleri
Doğruluk: İşlevi doğru mu?

Test: Yeterli mi?

Basitlik: Gereksiz karmaşıklık var mı?

Tutarlılık: Mevcut kodla uyumlu mu?

Performans: Belirgin yavaşlama var mı?

Güvenlik: Risk var mı?

Dokümantasyon: Gerekli mi, güncel mi?

Lisans: Yeni bağımlılık GPL uyumlu mu?

6.2 İnceleme tonu
Yapıcı. "Bu yanlış" yerine "Şunu düşündün mü?"

Nazik. Katkıcı gönüllü.

Somut. Belirli satır/konu.

Açıklayıcı. "Neden" belirt.

Teşekkür. Emeği tanı.

6.3 Yanıt süresi
İlk yanıt: 1 hafta içinde.

Tam inceleme: 2 hafta içinde.

Gecikme: Kısaca bilgi ver.

6.4 Reddetme
Nazikçe.

Gerekçeli.

Alternatif öner.

Teşekkür et.

Örnek:

"Katkı için teşekkürler! Ancak bu özellik kapsam dışında (Karar 04). Yol haritasında v1.2'de değerlendirilebilir. Şimdilik bir issue açalım mı?"

6.5 Onay
En az 1 onay (self-review dahil).

CI yeşil.

Çakışma yok.

DCO imzalı.

6.6 Birleştirme
Squash merge (varsayılan): Tek commit.

Rebase merge: Temiz geçmiş.

Merge commit: Nadiren.

Karar: Squash merge (basit, temiz).

7. Yönetişim (Governance)
7.1 Mevcut model: BDFN
Benevolent Dictator For Now (şimdilik iyi kalpli diktatör):

Tek geliştirici son kararı verir.

Katkılar dinlenir, tartışılır.

Şeffaflık: kararlar docs/kararlar/ altında.

Gerekçe yazılı.

Neden BDFN?

Tek kişi, hızlı karar.

Net sorumluluk.

Topluluk küçükken etkili.

Sınırlar:

Keyfi karar yok.

Yazılı gerekçe zorunlu.

Topluluk geri bildirimi dinlenir.

Şeffaflık esastır.

7.2 Gelecek model: Maintainer ekibi
Ne zaman?

Topluluk > 20 düzenli katkıcı.

Tek geliştirici yükü kaldıramıyor.

2+ yıl aktif proje.

Nasıl?

Düzenli katkı verenler arasından seçim.

Davet usulü.

Roller: Maintainer, Reviewer, Contributor.

Oylama: Basit çoğunluk.

Roller:

Rol	Yetki
Owner	Son karar, marka, yayın
Maintainer	Merge, sürüm, yol haritası
Reviewer	PR inceleme, test
Contributor	Katkı, issue, tartışma
User	Kullanım, geri bildirim

19. Özet
NexAlbum bir topluluk projesidir. Bu karar:

Kanallar: GitHub Issues, Discussions, PR (birincil); Discord (ileride).

Katkı türleri: Kod, şablon, profil, çeviri, doküman, test, tasarım.

Süreç: Fork → branch → kod + test → PR → inceleme → birleştirme.

DCO: Zorunlu; CLA yok.

Kod inceleme: Yapıcı, gerekçeli, zamanında.

Yönetişim: Şu an BDFN; gelecekte maintainer ekibi.

Davranış: Contributor Covenant 2.1.

Tanıma: AUTHORS.md, sürüm notları, teşekkür.

Destek: Şablon yanıt, SSS, sınırlı süre.

Katkıcı deneyimi: good first issue, mentor, sabır.

Dil: Türkçe + İngilizce; kod İngilizce.

Şeffaflık: Tüm kararlar kamuya açık.

Sürdürülebilirlik: Topluluk, projenin sigortası.

Bu karar, 02 (Açık Kaynak) ve 04 (Tek Kişi) kararlarının topluluk boyutudur. Tek geliştirici yükünü paylaşmak, projenin uzun ömürlü olmasını sağlamak ve kullanıcı memnuniyetini artırmak için topluluk katkısı teşvik edilir. Ama topluluk beklenmez; proje tek başına da çalışır.

Onay: Bu karar, ürünün topluluk ve katkı temelinin belgesidir.
